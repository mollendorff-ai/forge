# ADR-078: A Way In for Each Reader

**Status:** Proposed (2026-11-23)
**Date:** 2026-11-23
**Decided by:** the maintainer, who asked (2026-11-23) to make Forge easy, trustworthy and fun to adopt for new users, developers, maintainers and AI agents, and who accepts this by merging it. The review and the design are Claude's, in a session configured for Opus 5.5
**For:** roadmap A1-DOCS-MAP, and the order of A2 to A10. It supersedes, for documentation only, "adoption is not a goal" (2026-11-16)

---

## Context

Found on 2026-11-23 by installing 10.0.0-rc.34 with `install.sh --examples`, running `examples/bagel` (calculations, simulations, games), writing small models with mistakes in them, calling `forge mcp`, and then reading every README and every page in `docs/`.

**What there is.** About 400 KB of Markdown, most of it reference or showcase, and much of it held true by a test:

| Page | What it is | What keeps it true |
| --- | --- | --- |
| `README.md` | The front page: four ways to use Forge, four questions answered, the checks | `readme_commands.rs` runs every `$ forge` block; `doc_counts.rs`; `install_script.rs` |
| `docs/FEATURES.md` | The reference: the model file, every command and analysis | `doc_counts.rs` (counts only); `studio/tests/help.mjs` keeps the 15 headings Studio's "?" links to |
| `docs/EXAMPLES.md` | A long walk through models, mostly Monte Carlo | `doc_examples.rs` runs every model and number |
| `docs/posts/` | Eight questions, each answered with one command on `examples/` | `posts.rs` runs each and compares the output |
| `docs/PROMPTS.md` | Seven prompts for an AI, each run by a fresh agent | `install_script.rs` (the install line); the agents' runs, by hand |
| `docs/WORKFLOWS.md` | Four ways of working, as diagrams | `workflows_doc.rs` (commands exist, links resolve) |
| `docs/MCP.md` | The MCP server and its tools | `doc_counts.rs` (functions, and the tool count since A0) |
| `docs/cli/README.md` | Every command's `--help` | Generated by `make docs-cli`; equal to the binary's help on 2026-11-23, but nothing checks it |
| `docs/GLOSSARY.md`, `docs/REPORT.md`, `docs/STABILITY.md`, `docs/FUNCTIONS.md` | Terms, one command, the promise, the functions | `doc_counts.rs` for FUNCTIONS; nothing for the others |
| `examples/*/README.md` | Each example's story and numbers | The numbers of `examples/bagel` are asserted in `src/cli/commands/examples/` |
| `studio/README.md`, `forge-wasm/README.md`, `schema/README.md`, `editors/vscode/README.md` | How each part is built | Nothing |
| `CONTRIBUTING.md` (35 lines), `CLAUDE.md`, `docs/architecture/` | The rules and the design | `conventions.rs`, `no_skipping.rs`, `architecture_docs.rs` |

**What a reader cannot find.**

- **A new user** finds no order to learn in. `examples/starter.yaml` is the best first page Forge has, and its comments teach the two kinds of group. After it, the model file is one section of FEATURES.md that also explains eight format versions, and the analyses are reference sections. No page says what to do after `forge calculate`: that it rewrites the file (and keeps `.bak`), that `forge validate` is the gate for stale values, how `forge edit` and `git diff` fit. The error messages teach well ("Unknown name: plan.revnue. Did you mean 'plan.revenue'?"), and no page says so.
- **Someone using Forge with an AI** has seven good prompts and an MCP reference, but no first ten minutes in a real client (what to say, what comes back), and nothing to put in their own project's instructions for an agent. The MCP server's own `instructions` are already a short card of the rules an agent needs.
- **Someone building a pipeline** has diagrams. WORKFLOWS.md says that no whole pipeline without AI has been run, and the one with AI has run once (Sentinel).
- **A developer who embeds Forge** (the library, the REST API, forge-wasm) has the crate's docs.rs page, whose first line still says "YAML formula calculator with Excel-style arrays", and a REST section in FEATURES.md.
- **A contributor** has 35 lines: no Rust version, no wasm target, no Gnumeric, R or Node for the validation suites and Studio's tests. **A maintainer** has no page on making a release beyond `release.yml`.
- **Studio** can open only a bundled example from a link (`?example=`, `?model=`), so a lesson, or an AI's answer, cannot hand the reader its own model.

The readers of ADR-077 still hold: people who use GitHub, who read Markdown there, follow links into a repository and read YAML. Studio links its help to GitHub at the running release's tag.

## Decision

### 1. Five readers, and the page each starts on

| Reader | Starts on | Then |
| --- | --- | --- |
| A new user, with or without a terminal | `docs/guide/README.md`, from the README's first screen | The lessons in order; Studio's guide; the reference when a lesson links to it |
| An AI agent, or a person working with one | `docs/guide/ai.md` | `docs/PROMPTS.md`; `docs/MCP.md`; the agent rules template |
| Someone building a pipeline | `docs/guide/pipeline.md` | `docs/WORKFLOWS.md`; the CLI reference |
| A developer who embeds Forge | `docs/EMBEDDING.md` | docs.rs; `forge-wasm/README.md`; FEATURES.md's REST section |
| A contributor or maintainer | `CONTRIBUTING.md` | `CLAUDE.md`; `docs/MAINTAINING.md`; `docs/architecture/` |

`docs/README.md` is the index: these five rows, then every page by what it holds. The README's documentation table links to it.

### 2. The guide is lessons; the reference stays where it is

`docs/guide/` holds lessons, read in order:

| Page | What the reader does |
| --- | --- |
| `01-first-ten-minutes.md` | Opens the bagel in Studio or installs Forge, calculates it, changes the price, sees what moved |
| `02-a-first-model.md` | Writes the bagel shop from an empty file: scalars, a table, a formula over both, `_includes`, scenarios |
| `03-keeping-a-model.md` | Changes it the way a model is kept: `forge edit`, `forge calculate` (and `--dry-run`, `.bak`), `forge validate` as the gate, `git diff`, `forge upgrade` |
| `04-what-if.md` | Scenarios, break-even, goal seek, the tornado |
| `05-how-likely.md` | Makes inputs uncertain and reads `forge simulate`: percentiles, drivers, why the mean is below the plan |
| `06-what-will-they-do.md` | The price war: a game from the model's own numbers, its equilibrium, a tournament, the city's dynamics |
| `07-excel.md` | `forge export` and `forge import`, and what does not cross |
| `08-when-forge-says-no.md` | The messages a model gets most, each with what it means and the fix, copied from the binary |
| `ai.md`, `pipeline.md`, `studio.md` | The three ways in that are not the terminal |

FEATURES.md, FUNCTIONS.md, MCP.md, cli/README.md and GLOSSARY.md stay the reference, and the lessons link to their headings instead of repeating them. The 15 headings Studio's help links to stay as they are. The posts stay: a lesson links to the post that answers its question.

### 3. How a lesson is written

- **One model throughout: the bagel shop.** A lesson's model at its end is a file in `examples/guide/` (`02-bagel.yaml`, `05-bagel-uncertain.yaml`), so it runs in the tests and opens in Studio.
- **One idea a section,** each with the YAML, the command and what Forge printed.
- **It ends with "Check it yourself"**: one result worked out another way (by hand, in a spreadsheet, a line of Python), because a page whose numbers come from Forge proves only that Forge ran.
- **It ends with a challenge** ("find the price that gives an 80% chance of a profit", "stop the price war"), whose answer is under a `<details>` and is checked by the tests like any other number.
- **Plain words, written as the rest of the docs are written:** what the reader does and sees, the term defined where it is first used, and no claim that a test does not hold.

### 4. Each page is kept true by a test, from its first commit

`validation/repo` gets `guide.rs` (roadmap A2-GUIDE-TESTS), written before the first lesson:

- every `$ forge` block in `docs/guide/` is run and prints what the page shows, as `readme_commands.rs` does for the README;
- every `yaml` block headed by a file name (`# examples/guide/02-bagel.yaml`) equals that file;
- every link and anchor resolves, as `architecture_docs.rs` checks for the architecture pages;
- every `<details>` answer is one of the numbers the page's commands print.

The other new pages are checked the same way where they show commands, and `docs/cli/README.md` gets a check that it equals what `make docs-cli` writes from the binary. A page that cannot be checked by a test (Studio's guide, whose screenshots `studio/screenshots.mjs` makes) says where its claims come from.

### 5. What this does not add

- **No documentation site or generator.** The readers read Markdown on GitHub, Studio links there at the release's tag, and a site would be a build of its own to keep.
- **No copy of the reference in the lessons.** A lesson links to FEATURES.md's heading for the rest.
- **No translation.** P-STUDIO-FRENCH's reasons apply to the docs too.
- **Whether `llms.txt` earns its place** is decided in A5, from whether an agent that reads it does better than one that runs `forge --help`.

## Consequences

- A new user has an order to learn in, built on the example the README already tells them about, and every number they meet is held by a test.
- About ten new pages to keep. Each is tested, so a change to Forge that makes one wrong fails a pull request instead of reaching a reader.
- FEATURES.md, the posts and the examples do not move, so nothing that links to them (Studio's help, other repositories, the README) breaks.
- The order of the work is the roadmap's: A2 before any lesson; A3 to A9 in parallel; A10 (the README as the front door, then a trial by a fresh reader of each kind) last.
